## 2025-03-05 - Fix Error Information Leakage
**Vulnerability:** Found 7 instances in `server.ts` where internal application errors and stack trace details (`error.message`) were passed directly back to clients in `500 Internal Server Error` responses. In addition, the Express `x-powered-by` header was enabled, disclosing the server technology stack.
**Learning:** This is a systemic issue across all API endpoints indicating a missing centralized error handling pattern. Returning raw errors to clients breaks the principle of "fail securely" and could expose sensitive data like internal paths, query syntax, missing environment variables (e.g. GEMINI_API_KEY), or downstream service failures.
**Prevention:** Always log the original error internally (e.g., `console.error`) and return a generic, safe error message to the client. Consider implementing a global error handling middleware in Express to catch all exceptions and format them consistently, rather than handling it individually in every route block. Additionally, always disable the `x-powered-by` header using `app.disable("x-powered-by");`.

## 2025-03-05 - Fix In-Memory Type Confusion Vulnerability
**Vulnerability:** Found a lack of type validation for user-supplied inputs (`projectId`, `user`, `projectData`) in the `/api/cloud-sync/save` endpoint in `server.ts`. These inputs are directly used as keys in a JavaScript `Map` (`projectStore`) and properties in an `Array` (`collaborationActivityLog`). Passing unexpected types like objects (e.g., `{"projectId": {}}`) could lead to type confusion, memory leaks (if unique object references continually create new map entries where strings were expected), or application crashes.
**Learning:** The application heavily relies on in-memory data structures for state management (instead of a traditional database) which bypasses standard database-level schema validations. Because JavaScript Maps accept objects as keys, an attacker can trivially create runaway memory allocation by sending an infinite number of distinct objects in place of a string ID.
**Prevention:** Always implement strict type validation (e.g. `typeof param === 'string'`) at the application boundaries before inserting user data into in-memory structures. Consider using robust schema validation libraries (like Zod) for all API endpoints to guarantee input shapes and types automatically.
